Repository Knowledge Management

Like PKM, but for your repo. Todos, bugs, decisions and specs live with the code, where you and your agents already look.

In repo vs. out of repo

Where should project knowledge live?

I've tried both. Wikis and trackers are tidy until they drift from the code they describe. Notes in the repo stay true, and every agent can read them without a login.

Out of repo — wiki, tracker, ~/notes

Separate from the code

  • Drifts the moment the code changes
  • Agents need an integration, a token, or a copy-paste
  • Scattered across tools, one per project
  • Doesn't follow a fork, a clone, or a branch
In repo — rkm/

Next to the code

  • Changes land beside the commits that caused them
  • Any agent reads it with cat and grep
  • Reviewable, searchable, works offline
  • Links between specs and source are checked
The catch

A todo list churning through your pull requests is noise.

So rkm keeps knowledge on its own orphan branch: in the repository, never in your code history or worktrees.

Orphan means it shares no history with your code, so it never merges in. Optionally, every project's knowledge can share one folder.

Default: its own orphan branch

In the repo, out of your way.

By default, knowledge lives on an orphan _rkm branch with its own history, checked out once, beside your repo or in one folder for every project. Add to it from any worktree, any agent, any time, and your code branches never see it.

Clean worktrees

No rkm/ folder in your code, no knowledge commits in your PRs, nothing to merge between feature branches.

Found from anywhere

rkm path finds the knowledge checkout from any worktree or subdirectory, so every agent writes to the same place.

Still in the repo

It's a branch: push it, fetch it, clone it. Native jj workspaces when you use jj, git worktrees otherwise.

Recommended: one knowledge folder

Every project's knowledge in one place.

Out of the box, each repo's knowledge sits in a sibling folder. Set a workspace root once and rkm checks every project out side by side instead. That's the PKM part: one folder you can search, browse and open as a whole.

Search across projects

One rg answers "where did we decide this?" for every repo at once, and agents can borrow context from a neighbouring project.

Open it as one vault

Point your editor or notes app at ~/rkm and browse all your project knowledge like a personal knowledge base.

Tidy code folders

No -rkm folder beside every repo. Each clone gets its own subfolder, so same-named repos never collide.

Simple structure

A folder per kind of thing.

Each document is one Markdown file. The tool owns the frontmatter, file names and index; you write the bodies.

todos/Planned work, one item per file. open | done
bugs/Behaviour that's wrong, with a repro. open | done
decisions/Why the project is the way it is. Numbered, one call per file.
spec/How a feature behaves.
roadmap/Multi-phase plans.
process/How to make a kind of change.

The CLI

Small commands, one job each.

The tool is the only thing that edits frontmatter, file names and the index. That's what keeps a bundle written by five agents consistent. Every command is listed at the bottom.

Set up

Optionally pick one folder for all your knowledge, then start a bundle in any repo.

$ rkm config --workspace-root ~/rkm   # optional, once
$ rkm init                            # per repo

Capture

Slugs come from the title. Templates fill in the body headings.

$ rkm new bug --title "Parser drops trailing comment"
$ rkm new spec --title "Query grammar"
$ rkm adopt docs/design.md spec   # bring old notes in

Track

Todos and bugs carry state. Closed work drops out of ls.

$ rkm ls --type todo
$ rkm close swap-regex-engine --note "done in 9f1e0d"
$ rkm status query-grammar stable

Reorganise safely

Renames rewrite every link. Deletes are refused while anything still points at the file.

$ rkm mv todos/swap-regex-engine todos/adopt-re2
$ rkm rm todos/adopt-re2
rkm: todos/adopt-re2 is still linked from: rkm/spec/query-grammar.md

Commit

Conventional Commits by default, or your team's own template and pattern.

$ rkm commit --summary "record parser bug"
# message: docs(bug): record parser bug

Find it

It's just files. Use whatever you already use.

$ rg -l regex "$(rkm path)"
$ rkm ls --json | jq '.[].title'
$ rkm check            # run it in CI
Also

Built for agents, kept honest by people.

AGENTS.md, managed

rkm agents --write adds a short marked section telling any agent where the bundle is and how to use it. Rerun to refresh it.

Every write is signed

Set RKM_ACTOR=claude/opus-5.5 and each document records who wrote it and when.

Human sign-off

rkm verify marks a document as checked by a person. Agents are refused.

Safe in parallel

An OS lock serialises index and log writes, so several sessions can add notes at once.

Never pushes

RKM commits knowledge; it never pushes. Set a push_policy to tell agents your rule.

Typo-proof config

One optional config.toml per repo. Unknown keys are errors, not silent no-ops.

Reference

Every command.

That's the whole tool. rkm --help prints the same, and an <id> can be a concept id, a path or a unique slug.

Setup and storage

rkm init [--branch B] [--workspace PATH]
Start a bundle on its own orphan _rkm branch.
rkm init --in-tree
Start a bundle in rkm/, committed with the code.
rkm migrate [--workspace PATH]
Move an in-tree bundle to the knowledge branch, uncommitted notes included.
rkm config [--workspace-root PATH]
View or save the one folder for every project's knowledge.
rkm path
Print the bundle's directory.
rkm workspace add [--workspace PATH]
Reattach existing knowledge history.
rkm workspace remove
Remove a clean checkout; the history stays.
rkm commit --summary TEXT | -m MESSAGE
Commit knowledge using the repository's message policy.

New clone? Fetch the branch (git fetch origin _rkm); the next rkm command attaches it.

Documents

rkm new <type> [<slug>] --title T [--description D]
Create a todo, bug, request, spec, decision, roadmap or process.
rkm adopt <path> <kind>
Add frontmatter to an existing file; a file outside the bundle moves in, links rewritten.
rkm set <id> title|description|tags|to <value>
Change one field.
rkm retype <id> <type>
Change the type; the file stays where it is.
rkm touch <id>
Restamp generated after rewriting a body.
rkm mv <id> <new-id>
Rename and rewrite every link to it.
rkm rm <id>
Delete; refused while anything links to it.

Lifecycle

rkm close <id> [--note N]
Mark a todo or bug done.
rkm reopen <id>
Open it again.
rkm state <id> <state>
A state between open and done, such as asked.
rkm from <id> <origin>
Record another place that asked for it.
rkm status <id> draft|stable|deprecated
The document's lifecycle, separate from progress.
rkm verify <id>
Human sign-off; refused for agents.

Finding and checking

rkm ls [--type T] [--state S] [--all] [--json]
List documents; closed and deprecated are hidden unless asked for.
rkm index
Regenerate index.md.
rkm check
Conformance of frontmatter, links and index; run it in CI.

Agents

rkm agents [--write]
Print or update the managed AGENTS.md section.

The full rules and command examples.
